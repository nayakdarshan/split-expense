## Landscape (Layer 1 / 2 / 3)

- **L1, tried and true:** a group ledger with per-person net balances, a settle-up record and a min-transfers simplifier. Splitwise, Tricount, Settle Up and Spliit all converge on this shape. The model is solved, and the hard parts are rounding, multiple currencies and sync.
- **L2, current market:** Splitwise's free tier now caps expenses per day and shows ads (Trustpilot 2025 reports, Finny 2026 guide). That pushed users to Spliit (open source, free, no login), Tricount (free, bunq-owned) and Settle Up. The "alternative without the daily cap" category is crowded.
- **L3, first principles:** Splitwise's moat is the **network** (your friends are already on it), not the features. A feature-parity clone does not beat it on features. It wins only where the network is small and closed (your own flatmates, trips and family), where a Pro-only feature (scan, convert, charts) is the daily pain, or where it fits a local payment rail (UPI) that Splitwise handles poorly in India.

## Section 1: Architecture Review

```
  Phone (PWA, 390px)                         Vercel (Next.js App Router)                  Supabase (dev | prod)
  +-------------------------+   RSC/fetch   +---------------------------------+  PostgREST  +-----------------------------+
  | App shell, bottom tabs  |-------------->| Server Components (read)        |-----------> | tables + RLS                |
  | Add-expense sheet (FAB) |   Server      | Server Actions (write) -------- |---rpc()---> | create_expense/update_...   |
  | SW: precache + SWR read |   Actions     |   zod validate -> lib/money     |             | record_payment (plpgsql)    |
  +-----------+-------------+               |   splits computed in TS         |             | views: group_balances,      |
              |                             | /auth/callback (OAuth code)     |             |        friend_balances      |
              | Google OAuth                +---------------+-----------------+             | trigger: expense_history    |
              v                                             |                               | Auth (Google only)          |
       accounts.google.com <-------------- Supabase Auth ---+                               +-----------------------------+
                                                            +--> Sentry (errors)  [O1]
  lib/money (pure TS): minor units, allocate(), split modes, simplifyDebts(). No I/O; property-tested.
```

- **Boundaries:** reads go through RSC with the user's session cookie (`@supabase/ssr`). Writes go through Server Actions → RPC, so the invariants live in the database [A1]. The service-role key is **never** used in request paths. It is reserved for tests and seed scripts.
- **State machine, expense:** `active --edit(v=n)--> active(v=n+1)`; `active --delete--> deleted (deleted_at set)`; `deleted --edit--> REJECTED` (the RPC checks `deleted_at is null`); restore comes in v1. Invalid transitions are prevented inside the RPC, not the UI.
- **State machine, invite link:** `active --revoke--> revoked`; `active --join--> active` (multi-use); `revoked --join--> REJECTED`. The token is 128-bit random and only its SHA-256 is stored.
- **Coupling:** the balance views depend on `expense_payers` and `expense_shares`. That coupling is justified, since there's a single source of truth and no cached balance column that could drift.
- **Scaling:** for a personal circle, the first thing to strain is the `group_balances` view scanning all of a group's rows. At 10× it's fine. At 100× (thousands of expenses per group) it needs an index on `(group_id) where deleted_at is null` and can become a materialised summary later. That's a non-issue for MVP.
- **Single points of failure:** Supabase (DB and Auth), Vercel and Google OAuth. All are managed, and the cached shell keeps balances readable during a blip.
- **Rollback:** Vercel instant rollback to the previous deployment (under 1 minute). Migrations are additive-only during MVP, so old code keeps working on the new schema.
- No artifacts-about-the-work were added. Findings: **A1 (CRITICAL), resolved by D12.**

## Section 2: Error & Rescue Map

```
  CODEPATH                         | WHAT CAN GO WRONG                        | ERROR CLASS
  ---------------------------------|------------------------------------------|---------------------------
  /auth/callback                   | user cancels / code exchange fails       | AuthCallbackError
  joinGroupByToken (action->rpc)   | token revoked/unknown                    | InviteInvalidError (P0001 'invite_invalid')
  createExpense (action->rpc)      | zod fails (amount<=0, >1e12, bad split)  | ValidationError
                                   | sums mismatch / non-member participant   | MoneyInvariantError (P0001 'sum_mismatch'|'not_member')
                                   | RLS denies (not a member)                | ForbiddenError (42501)
                                   | network / 5xx from Supabase              | UpstreamError
                                   | double tap                               | duplicate id -> 23505 -> treated as success (idempotent)
  updateExpense                    | version stale [E1]                       | StaleVersionError ('stale_version')
                                   | expense deleted meanwhile                | GoneError ('deleted')
  recordPayment                    | payer==payee, amount<=0                  | ValidationError
  removeMember                     | non-zero balance                         | MemberHasBalanceError
  any update via supabase-js       | RLS filters row -> 0 rows, NO error      | must check count -> ForbiddenError  <- silent by default

  ERROR CLASS          | RESCUED | ACTION                                   | USER SEES
  ---------------------|---------|------------------------------------------|-----------------------------------
  AuthCallbackError    | Y       | redirect /login?error=...                | "Sign-in cancelled, try again"
  InviteInvalidError   | Y       | render invite page error state           | "This invite link is no longer valid"
  ValidationError      | Y       | field errors returned from action        | inline field message
  MoneyInvariantError  | Y       | log + Sentry (should be unreachable)     | "Amounts don't add up" + keep form
  ForbiddenError       | Y       | log + Sentry                             | "You're not in this group anymore"
  UpstreamError        | Y       | keep form state, show retry              | toast "Couldn't save, retry"
  StaleVersionError    | Y       | reload expense, show diff                | "Changed by Asha, review and save again"
  GoneError            | Y       | navigate back                            | "This expense was deleted"
  MemberHasBalanceError| Y       | block action                             | "Settle ₹X first"
```

The rule: every Server Action returns a typed `Result<T, ActionError>`, with no `catch (e) {}` and no catch-all toasts. The **"0 rows updated" RLS silence** is the classic Supabase trap, and it's handled because every write goes through an RPC that raises explicitly. GAPS: 0 after A1, E1 and O1.

## Section 3: Security & Threat Model

| Threat | Likelihood | Impact | Mitigation in plan |
|---|---|---|---|
| IDOR: read another group by UUID | Med | High | RLS `is_group_member(group_id)` on every table; the helper is `security definer`, `set search_path = ''`, `stable` to avoid RLS recursion on `group_members` |
| Forge a debt onto a non-member, or onto a member who didn't participate | Med | High | RPC rejects non-member participants [A1]. Any member can add any member, which matches Splitwise's trust model; it's audited by history |
| Invite-token guessing or leakage | Low | Med | 128-bit token, hash stored, revocable; joining needs Google sign-in |
| Service-role key leak | Low | High | Server-only env, never prefixed `NEXT_PUBLIC_`; CI grep check; separate keys per project [D1] |
| XSS via description, notes or names | Med | Med | React escaping, no `dangerouslySetInnerHTML`, length caps (description 140, notes 2000) |
| Open redirect on `/auth/callback?next=` | Med | Med | Allow only same-origin relative paths |
| CSRF on Server Actions | Low | Med | Next.js origin check built in; keep `serverActions.allowedOrigins` unset |
| Amount overflow or negative values | Low | High | zod plus DB `check (amount > 0 and amount < 1e12)`; bigint |
| Audit trail | — | — | `expense_history` trigger records actor, before and after JSON |

No PII beyond name, email and avatar; no payment data (UPI VPA is in v1). The only new dependencies are well-known (`@supabase/ssr`, `zod`, `@sentry/nextjs`, `@serwist/next`). No issues remain open.

## Section 4: Data Flow & Interaction Edge Cases

```
  amount "1,234.5" --parse--> 123450n minor --validate--> split(mode,...) --> shares[] sum==total --> rpc --> history+balances view
     |nil/empty -> field error   |>12 digits -> error   |0 participants -> error     |remainder -> deterministic   |stale -> E1
     |"abc"/"1.234" -> error     |0/negative -> error   |percent!=100 -> error        |   (order by member join order, then user_id)
```

- **Rounding rule (invariant):** `sum(shares) == total` exactly. The remainder of `n` minor units goes one unit each to the first `n` participants in a stable order: largest fractional remainder first, ties broken by `user_id`. Property-tested.
- **Async ordering (balances):** the invariant is that a balance equals Σ paid − Σ owed over active rows at read time. The only concurrent mutators are RPCs, each in its own transaction, and the view is computed at read time. Both orders of two concurrent `create_expense` calls give the same final view. Concurrent edits of the same expense are serialised by the version check [E1]: the second commit fails `where version = $v`.

| Interaction | Edge case | Handled | How |
|---|---|---|---|
| Save expense | double tap | Y | client UUID as PK → duplicate insert treated as success; button disabled while pending |
| Save expense | navigate away mid-save | Y | Server Action completes server-side; activity shows it |
| Save expense | offline | Y (MVP) | save disabled with an "offline" banner (outbox in v1) |
| Split editor | participant removed after the shares were typed | Y | recompute; exact mode re-validates |
| Group list | 0 groups | Y | empty state with "Create group" and "Join via link" |
| Balances | everyone settled | Y | "All settled up" state |
| Settle up | balance changed since the screen opened | Y | the amount is only a suggestion; the payment is recorded as entered |
| Invite link | opened while signed out | Y | `next=` round-trip through login, then join |

**Data model (MVP):**
- `profiles(id=auth.uid, name, avatar_url, default_currency='INR', activity_seen_at)`

- `invites(id, group_id, token_hash, revoked_at)`
- `expenses(id uuid client-generated, group_id, description, notes, category, date, amount bigint > 0, currency, version int, created_by, deleted_at)`

- `expense_shares(expense_id, user_id, amount)`
- `payments(id uuid client-generated, group_id, from_user, to_user, amount, currency, method cash|upi|other, date, note, deleted_at)`
- `expense_history(id, expense_id, actor, op, before jsonb, after jsonb, at)`
- `activity(id, group_id, actor, kind, ref_id, summary jsonb, at)`
- Views: `group_balances`, `friend_balances`

**RPCs:**
- `create_expense`, `update_expense(p_version)`, `delete_expense`, `record_payment` and `remove_member` are security invoker.
- `join_group(token)` is **security definer**, because the joiner isn't a member yet, with `search_path=''`.
- `is_group_member()` is security definer and stable.
- History and activity rows are written by security-definer triggers; users have no direct insert grant on those tables.

## Section 1: Architecture review

- [P1] (confidence: 8/10) Data model above: security-invoker RPCs still go through RLS, so the child tables need INSERT/UPDATE policies scoped by the parent expense's group membership. Otherwise the RPC fails with 42501. This is plan content: policies on `expense_payers`/`expense_shares` check membership through `expenses.group_id`.
- [P2] (confidence: 7/10) Friend ledger (CEO D10): if two people add their first shared expense at the same moment, two `direct` groups could be created. The `direct_pairs` unique key plus `insert ... on conflict do nothing returning` prevents that.
- [P2] (confidence: 7/10) `join_group` must be security definer, because RLS hides the invite from non-members. Its body only resolves `token_hash` → group and inserts the caller's own membership row.
- Production failure to watch: a Google OAuth redirect URL mismatch once the Vercel domain exists. Handled by registering the prod URL, the dev-preview wildcard and localhost (a user setup step), plus the `/login?error=` path.

Dispositions: all three are plan content inside the approved CEO A1/C6 scope; no new choice.
